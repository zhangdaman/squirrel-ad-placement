## 1. 背景与目标

### 产品背景

短剧广告投放中，投手每天要面对：巨量 / 磁力(快手) / 腾讯多平台规则差异、海量素材的审核合规、ROI 波动的归因排查。这些经验散落在人脑、群聊和历史数据里，新人难复用、老人靠记忆。松鼠投放把这些沉淀成一个**随时能问、答案一致、越用越聪明**的 AI 投放伙伴。

面向 **5–300 人规模的投放团队**（投放公司、代理商、品牌方投放部门），围绕投手日常的两大核心环节 **「问」和「诊」** 打造智能助手平台，以知识库为底座实现 4 大业务价值：

- **提效**：日均节省 1–2 小时重复性工作
- **降本**：辅助日常分析，减少无效消耗 15–30%，提升整体 ROI
- **标准化**：统一团队知识口径、操作流程、复盘框架，降低个体差异
- **沉淀**：把团队「人脑经验」变成「组织资产」，形成越用越聪明的数据飞轮

### 北极星指标与 SLA

- **北极星**：响应时效达标率 = 在对应 SLA 内完成的请求数 / 总请求数
- **分链路 SLA**（按链路复杂度分级）：

| 链路 | SLA | 适用 |
|---|---|---|
| RAG 链路 | ≤ 8 秒 | 知识 / 规则 / 策略类问答 |
| MCP 链路 | ≤ 15 秒 | 单平台实时数据查询 |
| Agent 链路 | ≤ 60 秒 | 多步深度归因 / 决策推理 |

## 2. 竞品分析

### 2.1 竞品格局概览

当前市场玩家分为四类，本产品定位为**第五类「广告投放 AI 助手」**——融合前四类的部分能力，并以**企业私域知识库**为核心差异化：

| 类别 | 解决的问题 | 代表 | 局限 |
|---|---|---|---|
| 投放管理工具 | 操作效率（批量 / 托管） | 热云 AdsDesk | 重操作轻决策，不沉淀经验 |
| 广告情报平台 | 外部情报（竞品 / 素材） | AppGrowing | 看外部，不管自己投放决策 |
| 平台方 AI 助手 | 平台单点优化 | 腾讯妙问 / 智投星（巨量生态） | 绑定单平台，不跨平台、不沉淀私域 |
| 通用 AI 平台 | 通用 AI 能力 | ChatGPT / 豆包 / 文心 | 不懂投放专业、无实时数据、无平台对接 |
| **松鼠投放（本品）** | **投放全流程决策** | — | 以私域知识库为底座，问 + 诊贯穿决策链 |

### 2.2 竞品对比矩阵

| 能力维度 | 热云 AdsDesk | AppGrowing | 腾讯妙问 | 智投星 | 松鼠 |
|---|---|---|---|---|---|
| 跨平台投放管理 | ✓ 强 | ✗ 无 | ✗ 仅自家 | ✗ 仅巨量 | ✓ 中 |
| 平台公域知识问答 | ✗ 无 | ✗ 无 | ✓ 强 | ✓ 中 | ✓ 中 |
| **企业私域知识库 ⭐** | ✗ 无 | ✗ 无 | ✗ 无 | ✗ 需自建 | **✓ 核心** |
| Agent 智能决策 | ✗ 规则托管 | ✗ 无 | ✗ 无 | ✗ 需自建 | ✓ 中 |
| 素材审核诊断 | ✗ 无 | ✗ 无 | ✗ 无 | ✓ 强（仅巨量） | ✓ 中 |
| 效果归因（Agent 多步推理） | ✗ 无 | ✗ 无 | ✗ 弱 | ✓ 中（仅巨量） | ✓ 中 |
| 数据分析 | ✓ 中 | ✗ 无 | ✗ 无 | ✓ 强 | ✓ 中 |
| 对话式产品形态 | ✗ 看板 | ✗ 报表 | ✓ 中 | ✓ 中 | ✓ 中 |
| 新人培训辅助 | ✗ 无 | ✗ 无 | ✓ 有 | ✓ 有 | ✓ 中 |
| 开箱即用程度 | ✓ 高 | ✓ 高 | ✓ 高 | ✓ 高 | ✓ 中 |

> **核心差异化**：松鼠是唯一以「企业私域知识库」为核心的产品——竞品要么无私域沉淀、要么需客户自建。打法不是单项做到极致，而是把跨平台投放管理、Agent 决策、素材诊断、效果归因、对话形态**聚合到一个产品全链路覆盖**，以私域知识库为护城河。

### 2.3 差异化分析

松鼠的 **「问 / 诊」** 两场景覆盖投手完整决策链：遇到不懂来「问」，遇到问题需诊断来「诊」——不是单点工具，而是贯穿投放全流程的 AI 决策伙伴。三大差异化：

1. **私域经验沉淀**——把团队「人脑经验」变成「组织资产」（L1 平台规则 / L2 公域经验 / L3 私域复盘，tenant 隔离）
2. **跨平台统一工作台**——一个入口管巨量 / 磁力 / 腾讯三个平台
3. **Agent 驱动深度归因**——多步推理分析 ROI 下降根因、给出止损建议，而非单点查询

### 全局布局结构

- **共享外壳**：左侧 `#__sidebar`（按角色过滤的导航）+ 顶栏 `#__topbar`（全局平台切换器 + 视角切换 + 用户）
- **平台全局化**：投手锁定单平台，管理者可切「全平台汇总」，状态存 `localStorage(squirrel_platform)`
- **视角全局化**：`localStorage(squirrel_role)` 驱动左侧导航过滤，和团队管理的权限矩阵一一对应

## 6. 意图识别体系（23 个意图）

采用 **「一级场景分类 → 二级意图分类」** 的两层层级结构，降低每步分类难度；二级分类器基于 **Qwen2.5-7B**。

### 6.1 三层识别架构与前置处理

```text
缓存匹配 → 加载短期记忆 → Query 改写 → 三层意图识别 → 槽位检查 → 路由分发
```

- **高频缓存**：命中直接返回（不区分 RAG / Skill / Agent 来源），未命中走下游
- **Query 改写**：用对话历史的实体替换「它 / 那个 / 刚才」等指代，补全省略信息，把原始 query 改写为「语义完整、可直接处理」的问题（准确率从 60–70% → 85%+）
- **短期记忆**：维护 current_intent / slot_state / recent_turns，支撑指代消解与意图延续

| RPT.material_diagnosis | 单条素材效果差 / 跑不动 | 「M789 为什么跑不动了」 |

**通用场景 GEN（3 选 1）**：GEN.chitchat（闲聊）/ GEN.system_usage（系统怎么用）/ GEN.unclear（结合上下文仍无法判断的兜底）。

### 6.3 复合意图、意图切换、槽位与追问

- **复合意图拆分**：一句话含多意图时拆为 primary + secondary（同场景内最多拆 2~3 个），标注 relation = independent / dependent；超出提示分步提问
- **意图纠正 / 切换**：用户表达否定（「不是 / 不对 / 我的意思是」）触发意图重判；重判结合上一轮错误结果避免再命中；切换后已提取槽位（如 project_name）保留复用，不重新追问
- **槽位提取**：platform / project_name / plan_id / time_range / metric_type / genre / material_type；标注 source（user_query / memory / platform_context / context_inference / slot_inference）
- **追问控制**：每轮最多追问 1–2 个槽位，优先级 plan_id > platform > project_name > time_range > genre；clarification_round ≥ 3 时用默认值兜底（platform→「巨量引擎」、time_range→「昨天」、genre→「通用」）

## 7. 路由与四链路设计（RAG / MCP / Skill / Agent）

### 7.1 路由规则

```text
缓存未命中 → Query 改写 → 意图识别 → 路由判断 → 链路执行
```

根据「意图 + 改写后 Query」判断进入哪条链路（同一意图可命中多源，同类问题可走不同链路）：

| 链路 | 类型 | 适用场景 | SLA |
|---|---|---|---|
| **RAG** | 知识库检索 | 规则查询 / 操作指南 / 出价·定向·素材策略咨询 | ≤ 8s |
| **MCP** | 工具·数据查询 | 单平台实时消耗 / ROI / CTR / 计划状态 | ≤ 15s |
| **Skill** | 可复用能力单元 | 固定流程的数据加工（素材排行 / 日报生成等） | — |
| **Agent** | 多步决策推理 | 关停决策 / 深度归因 / 跨账号差异 | ≤ 60s |
| Text-to-SQL | 结构化数据 | MCP 单平台覆盖不到的**跨平台聚合**查询 | — |

### 7.2 RAG 链路（知识类）

检索 L1 平台规则 / L2 公域经验 / L3 私域复盘三级知识库 → 向量检索 + 重排 → 取证 + 来源标注 → 渲染。L3 强制按 tenant_id 过滤隔离。

### 7.3 MCP 链路（单平台实时数据，ASK-09）

- **工具注册**：向 LLM 注册一组 MCP 工具（如 `get_plan_data` / `get_account_settings` 等），调广告平台 API（巨量 / 腾讯 / 快手）拉实时数据
- **数据增强**：纯数字回答不够好——MCP 拉数后自动追加一次历史 API 取环比，由 LLM 生成简短洞察
  > 「计划 123 今天消耗 3,250 元，较昨日同时段 2,800 元 +16.1%，跑量正常；日预算 5,000 元，预计今日可消耗完毕」
- **异常处理**：API 超时 / 限流 / 无权限有对应兜底话术

### 7.4 Skill 链路（可复用能力单元）

Skill = 介于「单次工具调用」与「完整 Agent」之间的**固定流程封装**，可被 RPT 链路直接用、也被 Agent 复用。
> 例：**素材排行 Skill** —— 拉素材数据 → 按 ROI 倒序排序 → 模板填充输出。Agent 归因时直接复用，不重复实现。

已注册 Skill（3）：`material_ranking_skill` / `daily_monitor_skill` / `rejection_check_skill`。完整的 **Skill / MCP / RAG 工具清单 + 23 意图→执行链路映射**见 [`docs/skills.md`](./skills.md)。

### 7.5 Agent 链路（深度归因，RPT 复杂场景）

**触发**：深度分析计划异常根因（「短剧 A 的 ROI 为什么掉了」）。原因可能横跨素材衰退 / 账户设置 / 大盘变化多维，且每步结果决定下一步——必须动态决策。

**全流程（Planner → Executor → Verifier，含失败回退）**：

1. **Planner 任务拆解**（LLM 调用 #1）：把「为什么 ROI 掉了」拆成 5 个 Task；Task 1 完成后 2/3/4 可并行，Task 5 等数据齐全
2. **Executor ReAct 循环**（Thought → Action → Observation）：
   - Round 1：调 MCP `get_plan_data` → 确认 ROI 下降真实（第 24 天起 1.5 → 0.8）
   - Round 2：调**素材排行 Skill**（复用）→ 定位 M789 素材 CTR 4.5%→1.8%，时点吻合
   - Round 3：调 MCP `get_account_settings` → 近 7 天无人为改动，排除人为
   - Round 4：调 **RAG L3 私域库**（"素材衰退 + ROI 下降"）→ 命中 3 条历史案例（替换素材 + 放宽定向，3–5 天恢复）
   - 综合 4 轮 → 生成归因报告草稿 v1
3. **Verifier 质量门控**：四维检查打置信度；未达 0.85 阈值（如 0.55）→ 回退 Executor 补充（如 Round 5 补大盘数据）→ 复检通过才输出

> 该链路体现**三链路在 Agent 内协同**：MCP 取数 + Skill 复用 + RAG 检索，由 Planner/Executor/Verifier 编排，对应 P05 的「一键执行 + 止损区间」闭环。

### 7.6 Text-to-SQL（跨平台聚合）

当 Query 判为结构化数据查询、且 MCP 单平台调用无法满足（需跨平台聚合）时，走自然语言查询自有数仓的 Text-to-SQL 链路。实时数据（近 30 天）优先走 MCP（更实时），历史 / 聚合走数仓。

## 12. 离线 Pipeline 与知识库工程

知识库是松鼠的护城河（见 §2 差异化）。所有知识经统一离线 pipeline 入库，供在线 RAG 链路检索。

```text
文档接入 → 分块 → 元数据·标签标注 → 向量化 + 索引入库 →（QA 沉淀回流）
```

### 12.1 知识库三级全貌

| 层级 | 来源 | 内容 | 隔离 |
|---|---|---|---|
| **L1 平台规则库** | API 接入（巨量 / 腾讯 / 快手） | 官方投放规则、审核规范、违禁词库（违禁词特殊处理） | 公共 |
| **L2 公域经验库** | 运营维护 | 结构化（拒审案例库、行业 benchmark）+ 半结构化（跨平台 SOP、行业白皮书） | 公共 |
| **L3 私域经验库** | 客户上传 | 结构化（客户历史投放报表）+ 半结构化（客户 SOP / 复盘 / 审核经验）+ 非结构化（群聊导出 / 会议纪要） | **tenant_id 严格隔离** |

- **字段映射机制**（结构化数据）：首次上传规则匹配自动识别列名（「花费」→cost、「平台」→platform）→ 运营/客户管理员确认 → 保存为该模板映射规则 → 后续同格式自动套用
- **L3 隔离**：所有 chunk 携带 tenant_id，向量 DB 按 tenant 分片存储，检索时强制过滤；platform/genre 标签 AI 预填 + 管理员确认，confidence 默认「中」

### 12.2 分块策略（Word/PDF/PPT 层级感知）

| 规则 | 内容 |
|---|---|
| ① 标题层级切分 | 以 H2 为主要切分边界，一个 H2 下完整内容 = 1 chunk，记录 H1 为 `parent_title` |
| ② 长 chunk 二次切分 | > 500 token 按段落边界切，相邻子 chunk 保留 50–100 token 重叠（overlap）防语义截断 |
| ③ 特殊内容独立成块 | 表格整张 = 1 chunk（不拆行列）、完整列表 = 1 chunk、PPT 每 slide = 1 chunk |
| ④ 质量校验 | < 50 token 合并到相邻块、> 800 token 强制二次切、完全重复去重 |

### 12.3 元数据与标签标注

- **系统自动生成**（通用）：`doc_id` / `chunk_id` / `upload_time` / `parent_title` / `section_title` / `summary` / `keywords`
- **L1 API 额外字段**：`rule_id` / `rule_category` / `effective_date` / `version_tag`（直接映射）
- **标签体系**：`platform` / `genre` / `doc_type` / `confidence`；标注方式按层级——L1 API 直接映射、L2 运营确认、L3 AI 预填 + 管理员确认

### 12.4 向量化 + 索引入库

- **向量化模型**：`bge-large-zh-v1.5` · 1024 维（与前端知识库 mock 一致）
- **向量 DB 记录结构**：`{ id, vector[1024], metadata{doc_id/tenant_id/doc_type/platform/genre/confidence/version_tag/parent_title/section_title/summary/keywords}, content }`
- **L1 规则库额外 ES 倒排索引**：`{ rule_id, platform, rule_category, rule_name, content, effective_date, version_tag }`，支撑精确规则检索
- L3 按 `tenant_id` 分片，检索强制过滤隔离

### 12.5 QA 知识库与高频缓存沉淀

- **QA 对 5 来源**：① 用户点赞的优质回答 ② 平台帮助中心 FAQ ③ 规则类高频问题 ④ 固定 SOP 类 QA ⑤ 运营手动维护
- **相似问扩充**：每条 QA 入库时 LLM 自动生成 5–8 条语义相同、表述不同的变体问法（覆盖口语/书面/简短/详细 + 同义词如「抽烟=吸烟=烟草」），运营审核可增删
- **回流缓存**：高频、稳定、高置信的 QA 写入高频缓存层（对应 §6.1 缓存命中直接返回），形成「用得越多、答得越快」的数据飞轮

> 注：本章为文字提炼，分块质量自检清单、元数据字段全表、向量化配置表、QA 数据结构与写入条件等明细表格见原 PRD 第六章图表。

## 15. 技术风险与缓解

| 风险 | 缓解 |
|---|---|
| 意图识别准确率 | Query 改写前置(60–70%→85%+) + 23 意图分层 + 模糊追问 + 诚实兜底 |
| 链路时效不达标 | 分链路 SLA（RAG≤8s/MCP≤15s/Agent≤60s）+ 高频缓存 |
| 知识库时效 / 冲突 | L1/L2/L3 分层，来源可溯，tenant 隔离，越界明确兜底 |
| Agent 输出质量 | Verifier 四维质量门控 + 置信度阈值 0.85 + 失败回退重做 |
| MCP 跨平台局限 | 单平台走 MCP，跨平台聚合走 Text-to-SQL 数仓 |
| 视频审核需求 | 视频不做帧分析；内容可走「文字描述」这一**正常入口**或人工，预期不夸大（文字描述本身是正常诊断方式、非视频降级）|
| 监控误判 | 监控纯数据不做判断，判断收口到复盘 Agent |
| 多平台数据口径 | 平台全局化 scope，golden-data 一致性账本保证跨页自洽 |
